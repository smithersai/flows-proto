## 1. What this actually is: one routing doctrine, two payloads

The repo already has two implementations of "presence is registration, the path
is the name":

- `packages/fs` + `packages/registry` route **flows**: scan a tree without
  evaluating modules, derive names from paths, project the result onto CLI /
  MCP / HTTP surfaces, load bodies lazily.
- `packages/build-cli/Workspace.ts` routes **targets**: discover `BUILD.ts`
  files from a git listing, derive labels from paths, import lazily, index
  exports.

The artsy API unifies them. A `PACKAGE.ts` is a routed file whose payload is a
target map. A workflow directory (`workflows/fix-sentry-issue/`) is a flow
directory in the `Flow Directory.md` sense (SKILL.md prompt + colocated
metadata) whose runnable projection is *also a target* (`S.Agent.Diff`) living
in a colocated `PACKAGE.ts`. The final state:

- **One discovery substrate** (glob the tree, index under path-derived
  identity, never evaluate on scan) shared by the registry scanner and the
  target workspace.
- **Two authoring payloads** discovered through it: flow entries
  (`flow.ts`/`flow.mdx`/`SKILL.md`) and target packages (`PACKAGE.ts` /
  `WORKSPACE.ts`).
- **One projection story**: labels (`smithers //src:test`), CLI commands,
  MCP tools, and agent-invocable workflows all fall out of the same index.

Do not physically merge `packages/fs` and `packages/build-cli` in step one, but
every naming and identity decision below must keep this convergence possible,
because `workflows/*/PACKAGE.ts` files reference both worlds at once (a SKILL.md
prompt by relative path, and gate targets by imported Package property).

## 2. The target API, enumerated

This is the complete surface observed in force + whatsabi. Anything not listed
here is not in scope. (The `S` below is `import { Smithers as S } from
"@smthrs/targets"`.)

### 2.1 File model

- One `WORKSPACE.ts` at the root: `export const Workspace = S.Workspace(name, config)`.
- One `PACKAGE.ts` per participating directory:
  `export const Package = S.Package({ defaultVisibility?, targets: {...} })`.
- Discovery (normative comment, force + whatsabi root PACKAGE.ts): "PACKAGE.ts
  files are discovered automatically: the CLI globs the tree and indexes each
  file's Package export under path-derived labels (`//src:buildClient`,
  `//:deadCode`) **before the workspace runs**. Only targets passed to
  S.Package are public; consts that stay out of the map are private to this
  file. Other PACKAGE.ts files reference public targets as properties of the
  imported Package."
- Cross-package references are real ESM imports of sibling PACKAGE.ts modules:
  `import { Package as src } from "./src/PACKAGE.js"` then `src.srcs`.
- Labels come from the keys of the `targets` map, not from export names.
  Target names are camelCase (`//src:relayArtifacts`).

### 2.2 Workspace layers

`S.Workspace(name, { repository, cache: S.Cache({directory}), runtime,
packageManager, nodeModules, flags?, host? })`. Normative comment: "Every value
below is a layer; the config keys compose them, with dependencies between them
(nodeModules needs packageManager, both need runtime) wired by requirement.
`layer` remains an escape hatch for a workspace that wants to compose Effect
layers by hand."

- `S.Runtime.Node({ version } | { manifest })`
- `S.PackageManager.Pnpm({ manifest, lockfile, version? })`, `S.PackageManager.Yarn({ manifest, lockfile })`
- `S.Npm.NodeModules({ packageJson })`
- `S.Host({ bins: [...] })` — "a target using S.Host.bin('x') fails at graph
  load when the bin is not declared here, and at run start when the host lacks it."
- `S.Flags({ production: "--production" })`, consumed as `S.Flags.production`
  inside args arrays elsewhere in the tree.

### 2.3 Inputs and file sets

- `S.file("//package.json")` (workspace-absolute) and `S.file("SKILL.md")`
  (package-relative).
- `S.glob(["**", "!__tests__/**"])`; cross-package globs observed
  (`S.glob(["//src/**/*.stories.tsx"])` in `.storybook/PACKAGE.ts`).
- `S.Filegroup({ srcs })` where srcs is a glob or an array of targets
  (grouping build outputs: `S.Filegroup({srcs: [compileEsm, esmPackageStamp]})`).
- `S.gitDiff()` / `S.gitDiff({paths})` / `S.gitDiff({added})` /
  `S.gitDiff({paths, addedLines: regex})` — diff-derived file sets; an empty
  result makes a consuming agent target vacuously green.
- `S.ImportClosure({ entries })` — reachability-derived file set; "per-file
  resolution rows cached individually and shared across closures."
- `S.Files.difference(a, b)` — set algebra over file sets.
- `S.Markdown.CodeBlocks({ file, lang })` — derived filegroup of fenced code
  blocks as virtual type-checkable modules.

### 2.4 Tool references (late-bound against workspace layers)

`S.NodeModule.Bin("typescript", "tsc")`, `S.NodeModule("@artsy/cohesion")`,
`S.PackageManager.bin`, `S.Runtime.bin`, `S.Runtime.npx("pkg")`,
`S.Host.bin("aws")`.

## 3. Gap analysis: current → target

What carries over unchanged (do not rebuild):

- Label grammar and pattern parsing (`build-cli/Label.ts`).
- Workspace file discovery via `git ls-files` with validated listings and the
  walk fallback (`Workspace.ts`).
- The key-material law: injective type-tagged encoding, `EXECUTION_FORMAT`,
  implementation fingerprint over source roots, ambient identity
  (`Planner.ts`). Every new constructor must flow through this unchanged.
- Cache store with untrusted reads, atomic publication, remote read-through
  (`Cache.ts`).
- `Exec` action shape (env narrowing, secrets placeholders, timeouts, output
  bounds) and `SecretProxy`.
- Attr-walking dependency collection (`Target.make` `collect()`): `data:
  [src.srcs, tsconfig]` creating edges without label strings is exactly
  today's mechanism.
- Per-verb views (`attrsForKind` → `forKind`) — generalizes into flavor modes
  (check/write/fix).
- Registry discovery's progressive-disclosure doctrine for anything with a
  SKILL.md.

What changes shape:

- BUILD.ts → PACKAGE.ts + WORKSPACE.ts. Labels from the `S.Package` map, not
  export names. Public/private inverts: today every export is public; now only
  map entries are.
- Tool-named catalog (TsBuild, Vitest, EsLint, Dprint, BiomeCheck...) →
  generic `S.Shell.*` with late-bound bins. The tool-named targets are deleted
  (no-backwards-compat rule); any repo-specific convenience returns as a plain
  function in that repo's PACKAGE.ts (the artsy files show matrices as plain
  functions: `providerTest(provider)`, `example(name)`).
- `Config.Workspace` (cache dir only) → `S.Workspace` (identity + layer
  composition). `Install` → `S.Npm.NodeModules` wired by requirement.
- Verbs: `build|test|lint|run|docs` kinds → flavor-implied verbs plus modes.
  `docs` as a kind disappears; DocsParity-style checks become `S.Shell.Test` /
  `S.Agent.Lint` targets in this repo's own PACKAGE.ts files.
- GithubCiGen's current jobs/gates config → `S.Github.Workflow` declarations
  referencing targets, plus `CiGen` with `preserve` and drift check.
- LlmLint → `S.Agent.Lint` over the real agent stack (`@smthrs/agent` /
  harness), not a subprocess CLI wrapper. LlmLint's batching/limits carry over
  as implementation detail.

What is genuinely new (no current implementation):

1. Package visibility and the public-map inversion.
2. Artifact trees: `outDirs` as CAS-backed output manifests with
   materialization (`S.Materialize`, dependency-means-materialize). Today cache
   hits validate declared outputs but never restore files.
3. The resolver: `S.ImportClosure`, `S.Bundler.*.resolve`, per-file resolution
   rows, `S.Files` algebra, `S.Markdown.CodeBlocks` virtual modules.
4. Agent targets with payloads, gates feedback loops, write-set enforcement,
   MCP, approval, `onSuccess`.
5. Services (`Shell.Serve` + `readiness` + `services:` on tests).
6. Triggers (`S.Cron`) and outward-action targets (Publish/Release/Pages/Pr)
   with approval.
7. Sandbox policy (network default-off) as an enforced property, not a comment.
8. Typed authoring surface replacing `smithers.d.ts`.

## 4. Architecture decisions

### D1. Target identity: labels are assigned by the discovery index, not by values

The single most dangerous defect class in this migration is object-identity
drift. Today `Workspace.label()` already contains a workaround (see the long
comment at `build-cli/src/Workspace.ts:1160-1195`): tsx's programmatic import
can evaluate one BUILD.ts twice (CommonJS bridge vs ESM loader), producing two
object identities for one declaration, reconciled by (target-id, attrs-JSON)
matching. PACKAGE.ts makes cross-file ESM imports the *primary* referencing
mechanism, so this problem moves from corner case to main path.

Decision: the loader owns identity.

- All PACKAGE.ts modules load through **one** module loader instance with a
  canonical module cache keyed on canonical-path + content digest (extend
  `importNamespace`'s existing keying). Two spellings of one file must resolve
  to one namespace within a command.
- After import, the CLI walks the discovered `Package` export and **brands**
  each target value with its label (path-derived package + map key) via a
  non-configurable symbol property, exactly as `TargetTypeId` is attached
  today. Branding happens once, at index time, before any planning.
- A target value reached through an import is the same object the index
  branded (same loader, same cache), so `src.srcs` carries its label already.
  The `(target-id, attrs-JSON)` reconciliation stays only as a guarded error
  path that *fails loudly* on ambiguity instead of guessing.
- One value, one label stays law. `S.Alias` satisfies it by being its own
  target value whose metadata points at the aliased label; the graph gets an
  Alias node with one dependency, not a second name for the same node.
- This closes API-REVIEW.md open questions 1 and 2 (Flow-tag identity and the
  call-site-stack hint): the loader registry replaces the stack heuristic; the
  stack capture stays only to produce good error locations.

### D2. Discovery: eager index, lazy evaluation — and the fs precedent

"The CLI globs the tree and indexes each file's Package export before the
workspace runs" (normative). But importing every PACKAGE.ts on every command
would make graph load O(repo) and would run partner code the command never
needed. Reconcile the comment with today's laziness:

- The **file index** (which PACKAGE.ts files exist, at which package paths) is
  built eagerly from the git listing — this is cheap and is what "indexes ...
  before the workspace runs" needs to be true for label resolution and
  pattern expansion.
- **Module evaluation** stays lazy per package, exactly as `loadBuild` is
  today, with the ESM import graph pulling in dependencies naturally (loading
  `//:test` imports `./src/PACKAGE.js` transitively; nothing else evaluates).
- A `//...` pattern evaluates everything it matches, as today.
- Import cycles between PACKAGE.ts files: ESM permits them but a partially
  initialized `Package` binding read during a cycle is `undefined` at attr
  time. Detect at index time (the loader tracks in-progress imports, as
  `importing` does today for manifest resolution) and fail with the two file
  names and the advice the whatsabi comment models ("reach the library source
  via ImportClosure instead of importing src/PACKAGE.js" —
  `~/artsy/whatsabi/examples/PACKAGE.ts` documents exactly this escape).
- WORKSPACE.ts is loaded first, always: it is the layer environment every
  target resolves `S.Flags.*`, `S.Host.bin`, `S.PackageManager.bin` against.

### D3. Flavors replace kinds; modes replace verb-mapped attrs

Today a target declares `kinds: ["build","test",...]` and optionally
`attrsForKind`. The artsy API implies the flavor at the constructor
(`Shell.Test` *is* the test kind) and adds modes:

- Every flavor maps to exactly one primary verb (table in §2.5) plus a set of
  supported modes: `check` (default for Generate/Diff/Lint/CiGen), `write`
  (`--write`), `fix` (`--fix`). Internally modes reuse the existing
  `forKind`/verb-view machinery: a mode is a re-derivation of attrs, inputs,
  outputs, cacheability — and therefore a distinct cache key, which the
  current planner already guarantees.
- `verbGate` survives as flavor law rather than per-target config: `Shell.Run`
  and `Shell.Serve` never appear in `ci`/`test`/`build` plans, and never as a
  `data` dependency (see D5). Publish/Release/Pr/Commit are `run`-only and
  additionally approval-gated.
- The CLI's bare-label form (`smithers //:prePush`) resolves the flavor's
  primary verb; verb-first form (`smithers test //...`) filters by flavor as
  the planner filters by kind today.

### D4. The four edge types are distinct and typed

The artsy comments define a strict law: "A dependency edge always means
'materialize files', never 'execute'." But the files also use `gates:`,
`services:`, and `onSuccess:` — which *do* mean execute. The resolution is that
these are four different edge types with four different semantics, and they
must never be conflated:

1. **`data` edge** (attrs walk): consumer needs the producer's *files*. For a
   filegroup: its expanded members. For a Build/Copy/Pack: its artifact tree,
   restored from CAS on hit (never re-executed if keyed green). For
   `Npm.Published`: the fetched baseline. Producers that have no file output
   (`Run`, `Serve`, `Commit`, ...) are **illegal in data** — graph-load error.
2. **`gates` edge**: consumer requires the gate target to *execute (or hit)
   green first*, in the consumer's current tree state. Gates are ordinary
   test/lint/generate-check targets. For agent targets, gate failure is
   feedback, not termination (D7).
3. **`services` edge**: consumer requires the Serve target *running and ready*
   (readiness probe) for the duration of its own execution; the executor owns
   start, readiness wait, and teardown (D8).
4. **`onSuccess` edge**: fire-and-run after settle; failures of the follow-on
   do not un-settle the workflow.

Each edge type is separately represented in metadata and separately encoded in
key material (data edges contribute dependency keys as today; gates contribute
gate labels + keys; services contribute the serve target's identity but not a
"result"; onSuccess contributes nothing — it cannot affect the result).

### D5. Artifacts: outputs become CAS trees; Materialize closes the loop

Today `DeclaredOutputs` are verified but a cache hit restores nothing. The new
API is built on restoration (relay `__generated__` is gitignored and *only*
exists via materialization; `data: [recordFixtures]` must place `.cache/` on
disk for the test's sandbox). Required work, in `Executor`/`Cache`:

- On green execution of a target with `outDirs`, capture the output tree as a
  manifest of `(relpath, digest, mode)` plus CAS blobs (local
  `.flows/cas/`, remote `/cas`). `ToolBuild`'s `CaptureOutputs` and
  `measureOutput` are the seed; the flows3 queue's lane B
  (`@smthrs/artifacts`) started this — reuse it.
- On cache hit, admit the manifest (existing adversarial validation applies:
  the *target's declared* outputs choose what is verified, never the entry),
  then **materialize** blobs into the declared `outDirs` before any dependent
  runs (Materialized Inputs law). Hardlink from CAS where the filesystem
  allows; copy otherwise; never symlink into the CAS (a tool writing through a
  link would corrupt the store).
- Materialization must be crash-safe and non-interleaved: write to a temp
  sibling directory, fsync, rename-swap per `outDir` root; a killed
  materialization leaves either the old tree or the new tree.
- `S.Materialize(t)` is then a thin explicit target: "ensure t's artifacts are
  present in the working tree" for editors/dev servers.
- Output trees count as inputs downstream via the manifest digest, which is
  already what dependency keys encode.

### D6. The typed authoring surface

`smithers.d.ts` is a placeholder by design. The real `@smthrs/targets` must
type the whole S namespace for real, because PACKAGE.ts files are the product
UI. Constraints:

- Chainability shown in the examples must type-check: `S.Shell.Test({...})`
  returns a Target value usable in arrays, maps, and as `Package` properties;
  `rspack.resolve(...)` returns a value with `.files`/`.packages` that
  composes wherever a filegroup does; `examples.srcs` on an imported Package
  is typed.
- `S.Package({targets})` should propagate the target map type so importing
  packages get typed properties (`typeof src.relayArtifacts`), giving
  compile-time errors for renamed targets across files. This is the "typed
  route manifest" idea from `packages/fs/Route.ts` (`Route.Name` widening via
  declaration merging) applied to targets — same doctrine, target payload.
- The `yield*`/Effect-layer claim in smithers.d.ts is aspirational typing for
  a workspace escape hatch. Ship: workspace config values are (or wrap) real
  Layers with a documented `layer` escape hatch; do NOT make ordinary target
  declaration require Effect (the authoring surface stays plain declarative
  calls; the "model does not write Effect" ruling points the same direction
  for any file an agent authors).
- PACKAGE.ts files must type-check under the repo's normal tsconfig story
  without the `/// <reference>` hack once `@smthrs/targets` ships types. Keep
  the reference-directive path working for partner repos that vendored
  smithers.d.ts until their install migrates (delete in ours).

### D7. Agent targets sit on the real agent stack

`S.Agent.Lint/Diff/Pr` are targets whose action is an agent session. Design:

- The agent handle (`S.Agent.Codex("luna")`) resolves to a Layer-provided
  agent service (flows3-design D1: model choice is DI; the handle names a
  service configuration, and the *name* is key material, never keys/tokens).
- **Vacuous green is evaluated before session start**: expand `data`; if the
  gitDiff-derived slice is empty, settle green with a recorded "not invoked"
  result. This is a hard cost-control invariant with its own tests.
- **Write-set enforcement is mechanical, not prompt-level.** The session runs
  against a scratch overlay (worktree or overlay dir); on settle, compute the
  tree diff; any path outside `changes` (or `fixes` in fix mode) fails the
  target with the offending paths, and nothing is copied back. Only the
  in-set diff is applied to the real tree. Prompts may *tell* the model the
  write-set; the executor *proves* it.
- **Gates loop**: run gates (ordinary targets) against the candidate tree;
  on red, feed the structured failure output back into the session; bound by
  `maxRounds`; on exhaustion the target fails with the last gate report and
  the candidate diff preserved as an artifact for humans.
- `payload` decodes through `S.Input.*` schemas (bridge to
  `packages/fs/internal/SchemaBridge.ts` — the same machinery that turns
  input schemas into CLI flags today). "Missing payload fields are asked of
  the human": project payload schema onto an interactive prompt when the CLI
  is interactive, and fail with a structured "needs input" result when
  headless.
- `mcp:` entries become session tool servers; unreachable MCP fails early at
  session start (fix-sentry-issue comment: "the workflow fails early when it
  is unreachable instead of discovering that mid-run").
- Agent targets are never cacheable (nondeterministic bodies); their *gates*
  are the cacheable pieces. `Agent.Lint` in check mode may cache on
  (diff-digest, prompt digest, agent name) if and only if a `validate`-style
  admission gate exists — defer caching until then (flows3-design: validate
  gates admission).
- `approval: "required"` and the outward half of `Agent.Pr` go through the
  same approval mechanism as D9.

### D8. Services: Serve targets under tests

`services: [src.dev]` on `playwright.smoke` means: acquire the service, wait
for `readiness` (port open / probe), run the test, always release. Rules:

- Serve targets are resources with scoped lifetimes (Effect scope), not graph
  results. Their identity participates in the consumer's key (which server
  definition the test ran against) but there is no "output".
- Concurrency: two tests sharing one service within one command share one
  instance (refcount in the executor); distinct commands never share.
  Port collisions fail fast with the owning target named.
- A service's own `data` deps materialize first (the dev server needs relay
  artifacts) — ordinary data edges under D5.
- Teardown is guaranteed keep-going-safe: a test failure or interrupt still
  releases; leaked processes are a test-suite-blocking defect.

### D9. Outward actions and approval

`Npm.Publish`, `Github.Release`, `Github.Pages`, `Git.Pr`, `Agent.Pr`,
`deleteReviewApp` share one contract:

- Flavor `run`, unreachable from ci/test/build plans and from `data`.
- `gates` must pass (fresh or cache-hit green in the current tree) before the
  outward step begins; the outward step never starts on stale gate results
  (re-expand inputs at execution time, as the executor already does for cache
  admission).
- "Invoking the target is the consent" for interactive invocation; a target
  that additionally declares `approval: "required"` requires an explicit
  approval event even when invoked by an autonomous caller. Plumb through the
  existing human-request surface (registry/harness ask-human), not a bespoke
  prompt, so approvals are durable and auditable.
- Side-effect tiers from `packages/build/DESIGN.md` (sealed / compensable /
  irreversible) classify each: publish is irreversible (refuses undo with a
  typed error), PR-open is compensable (close), commit is compensable
  (reset). Keep the existing `ExecIrreversible` seam.

### D10. The resolver (ImportClosure, Bundler.resolve, Files algebra)

This is the largest new subsystem. Reference: Bazel Skyframe
(`reference/bazel` `src/main/java/com/google/devtools/build/skyframe/`) for
keyed, memoized, incremental evaluation; the artsy comments demand exactly
that shape ("per-file rows are cached individually and shared across
closures", "one file's dependency query costs only the rows not yet
resolved").

- Unit of work: `resolve(file, resolutionConfigDigest) → row` where a row is
  the file's parsed import/require/export specifiers resolved to (file |
  package | builtin | unresolved). Row key = (file digest, resolver-config
  digest, resolver-implementation fingerprint). Rows live in the same cache
  store as target results.
- `S.ImportClosure({entries})` = BFS over rows from the entry set; the
  closure's identity is the sorted (path, digest) list — the same shape as a
  filegroup expansion, which is what lets it compose "wherever a filegroup
  does" and feed `S.Files.difference`.
- Resolution config: for `ImportClosure` default to TS/JS resolution derived
  from tsconfig + package.json (`exports` maps); for `Bundler.Rspack`, derive
  from the tool's own resolve options ("reusing the tool's own resolve
  options" is normative). Getting Node/TS resolution exactly right is a
  swamp: state the supported subset explicitly (ESM + CJS requires, tsconfig
  `paths`, package `exports`/`main`, extension probing) and fail closed with
  `unresolved` rows listed in the closure result rather than silently
  dropping edges. `deadCode`-style assertions must treat `unresolved` as an
  error by default — a missed edge silently deletes "dead" live code.
- `S.Bundler.make` defines the generic two-phase contract (resolve target,
  build target keyed on the resolved graph); `Rspack` wraps it with the
  tool's CLI. The build's key includes the *graph* digest, not the universe
  digest — that indirection is the whole caching win and must have direct
  tests (edit a file not in the graph → build key unchanged).
- `S.Markdown.CodeBlocks` extracts fenced blocks into virtual files under the
  cache dir with stable names (file digest + block index) and presents them
  as a filegroup; `checkReadme` then compiles them with `buildTypes` on the
  path (the whatsabi example relies on package `exports` resolving to the
  local emit — an integration test target in the conformance suite).

### D11. gitDiff enrichment and the shared-branch trap

`S.gitDiff({paths, added, addedLines})` adds filtering to today's
base-vs-worktree diff. Two hard rules:

- The diff *content* (patch bytes) is key material as today, filtered
  before digesting so an out-of-scope edit does not re-key a scoped lint.
- Base selection: default merge-base against the default branch for CI
  (`affected: true` uses the same computation), explicit base for local. The
  known trap (memory: fixed-base ranges on shared main grow with wall clock)
  means: never bake a moving base's *resolved commit* into declarations;
  resolve at plan time and record it in the plan output.

### D12. CI generation

Implement the force shape as primitive: `Github.Setup` (emitted composite
action; cache URL/token secrets), `Github.Workflow` (name, triggers,
concurrency, setup ref, `affected`, `run: [targets]`), `Github.CiGen`
(collects workflows, `preserve` list of hand-written files, `changes`
write-set `.github/**`, check-by-default drift mode). Today's `GithubCiGen`
renderer is the seed; the "nothing in the declaration is a command" rule from
`packages/build/docs/reference/targets/github-ci-gen.md` stays law. `affected`
mode compiles to: checkout fetch-depth 0, merge-base diff, run the verbs with
the planner's existing input-intersection logic (new planner mode:
`--affected=<base>` computes which selected targets' expanded inputs intersect
the diff; everything else reports as hit/no-op). whatsabi's `Github.Ci` is
sugar over these or is cut (ask will; §9).

### D13. Cron and triggers

`S.Cron({schedule, refresh, run})` declares a trigger; the target renders into
the generated CI (a scheduled workflow) via CiGen and/or registers with the
flows trigger subsystem (`Concepts/Flow Triggers.md`, `Github Automation.md`
"the declaration is the door"). `refresh: [recordFixtures]` means: execute the
named Build targets *bypassing cache reads* (existing `readCache: false` path)
and publish new results; `run:` then executes against the refreshed store.
No new scheduler is built here; the declaration projects onto GitHub scheduled
workflows first (matching the whatsabi comment that the schedule replaces an
actions cron), and onto the internal trigger door when running under the flows
engine.

### D14. Sandbox posture: honest tiers

The artsy files write `sandbox: { network: true }` as if network-off is
enforced. Today there is no sandbox (`DESIGN.md` is explicit; effects are
"expected" not "hard"). Do not fake it. Tiered plan:

- Tier 0 (immediately): `sandbox` is declared policy; the executor enforces
  what it can without OS support — secrets are only injected where declared
  (already true), env stays narrowed (already true), and the declaration is
  key material. Documentation states plainly that network-off is not yet
  OS-enforced.
- Tier 1: process-level enforcement where cheap — macOS `sandbox-exec`
  profile / Linux unshare-net for `sandbox: {network: false}` targets
  (default), keeping a per-target opt-out. Gate cross-run cache admission of
  network-touching targets on the declaration as DESIGN.md already gates
  install actions.
- Tier 2 (later): the harness sandbox placement (`"use sandbox"`,
  `Concepts/Placement.md`) executes targets in real isolation.
  The key law from the Austin-research note applies: "use 'declared and
  revalidated' until isolation proves more" — never claim hermeticity from
  caching alone.

### D15. Naming and the two binaries

- Import stays `@smthrs/targets`, export `Smithers`, alias `S` by convention.
- CLI binary: `smithers` for partner-facing use (force AGENTS.md), keeping
  `smthrs` as the same binary under the old name only inside this repo until
  the port completes, then delete (no-backwards-compat).
- "Workflow" is banned in flows naming (2026-08-11 ruling) but `S.Github.
  Workflow` names GitHub's own artifact — that is GitHub's noun, not ours;
  keep it, and never use "workflow" for our own flow concepts in API names,
  docs, or errors. The `workflows/` directory name in partner repos is
  *their* tree; our docs call the things inside it agent flows.

## 5. The riskiest parts, ranked, with invariants and test obligations

This section is the point of the plan. Each risk names the invariant that must
hold every time, the failure mode if it does not, and the tests that pin it.

### R1. Identity and label integrity (highest risk)

Failure mode: one declaration under two identities → a target executes twice,
a dependent is released by the wrong node, or two labels answer with each
other's cache entries. This class is silent and corrupts caches durably.

Invariants:
- I1: within one command, one PACKAGE.ts file evaluates at most once, under
  one module namespace, regardless of import spelling.
- I2: every target value in any plan carries exactly one label, assigned at
  index time.
- I3: a value exported in two Package maps (same object under two names) is a
  graph-load error naming both labels (Alias is the sanctioned way).
- I4: an import cycle between PACKAGE.ts files is a graph-load error naming
  the cycle path, before any planning.
- I5: a target constructed outside any PACKAGE.ts (helper module) is legal
  only if it ends up in exactly one Package map.

Tests: dual-import (relative + index) evaluation-count tests; symlinked
spelling tests; cycle fixtures; the existing `one target value is exported
under both` test ported; property test — for random DAG fixtures, plan twice
and assert byte-identical plans.

### R2. Cache-key law under the new constructors

Failure mode: two different declarations share a key (poisoned cross-answers)
or one declaration's key drifts across hosts (cache never hits).

Invariants:
- I1: every new attr reaches key material through the existing injective
  encoder; no constructor bypasses `keyOf`.
- I2: mode (check/write/fix) is key material (distinct keys per mode) — the
  existing `forKind` guarantee extended.
- I3: agent name, prompt digest, MCP server identities, secret *names*,
  sandbox declaration, service identities, gate labels+keys are key material;
  secret values, tokens, host paths, cache directory never are.
- I4: bundler builds key on the resolved-graph digest, not the universe.
- I5: toolchain identity (runtime version, package-manager version, declared
  host bin versions where pinned) is folded into key material — this is the
  flows3 "turn the cache on" precondition; without it `cache: true` on
  Shell.* is wrong.

Tests: extend the existing key-material property tests to every new
constructor; golden-key fixtures across two checkouts at different paths;
negative tests that a secret value change does not re-key and a secret name
change does; graph-vs-universe bundler test from D10.

### R3. Write-set enforcement (changes / fixes)

Failure mode: a tool or model writes outside its declared write-set and the
change lands — the exact defect the write-set exists to prevent; for agent
targets this is the safety boundary.

Invariants:
- I1: for `Shell.Diff`, `Generate`, `Agent.*`: after execution, the observed
  tree delta is computed mechanically and any path outside the declared set
  fails the target and reverts/does-not-apply the delta.
- I2: write-set globs resolve against the *declaring package*, are validated
  at declaration (no `..`, no absolute, not into `.git`/cache — reuse
  `declaredOutputFailure`), and are key material.
- I3: check modes never write anything (drift computed in scratch space).
- I4: the enforcement mechanism itself cannot be bypassed by symlinks (a
  write through an in-set symlink to an out-of-set path is out-of-set —
  resolve real paths before judging; the repo's SafeFs discipline applies).

Tests: adversarial fixtures — tool writing a sibling file, through a symlink,
into `.git`, deleting out-of-set files; agent-session fake that attempts
out-of-set writes; crash mid-apply leaves the tree either untouched or fully
applied (temp + rename discipline as in `writeGeneratedFile`).

### R4. Artifact capture and materialization

Failure mode: a cache hit materializes a wrong or partial tree; a build reads
half-materialized inputs; the CAS is poisoned by a symlink or a path escape.

Invariants:
- I1 (Materialized Inputs law): no target dispatches until every data-edge
  file is physically present and digest-verified.
- I2: capture is exact — the manifest lists every file under declared
  `outDirs` and nothing else; overlap/duplicate rules from
  `declaredOutputsFailure` apply to observed trees too.
- I3: admission verifies blob digests before placement; placement is atomic
  per outDir root; concurrent commands on one workspace do not interleave
  (per-outDir lock or last-whole-tree-wins rename, choose and document).
- I4: CAS entries are immutable and content-addressed; nothing ever writes
  through a materialized hardlink back into the CAS (read-only modes on CAS
  files, copy-on-materialize where the platform cannot guarantee it).
- I5: gitignore interaction: materialized trees are ignored (relay
  `__generated__`), and the discovery listing already excludes replayable
  state — extend `inWorkspaceStateDirectory` to the CAS root.

Tests: kill -9 during materialization; tampered CAS blob (digest mismatch →
miss, never a crash or a placement); hardlink mutation attempt; two commands
racing one outDir; Windows/macOS path semantics (case-insensitive collisions
in manifests).

### R5. The dependency-edge law (data never executes Run/Serve)

Failure mode: an unattended plan starts a dev server or mutates state because
something depended on a Run target — the exact hazard the Verb.ts docblock
already guards for pipelines.

Invariants:
- I1: constructing an attrs graph in which a Run/Serve/outward target appears
  in `data` (or inside a Filegroup srcs, or reachable through one) is a
  declaration-time error, not a plan-time surprise.
- I2: `services:` accepts only Serve-flavored targets; `gates:` only
  test/lint/check-capable targets; `onSuccess:` anything runnable.
- I3: Suite tests-lists accept only test-capable targets.

Tests: type-level (must not compile where types can express it) plus runtime
fixtures for the dynamic paths; plan-output golden tests asserting Run targets
appear only as roots of explicit run invocations.

### R6. Agent-target loop discipline

Failure mode: unbounded token spend (vacuous-green not honored, gates loop
re-running an unchanged failing gate), or an agent "success" whose gates never
actually ran against the final tree.

Invariants:
- I1: empty expanded `data` → agent process is provably never spawned
  (assert via injected fake).
- I2: gates run against the exact candidate tree that would be applied, after
  every round, and the settle decision uses the last gate run's results — no
  TOCTOU between gate green and apply.
- I3: `maxRounds` is a hard bound; exhaustion is a typed failure carrying the
  final diff and gate report as artifacts.
- I4: `src.generated` as a gate (update-interfaces example) runs its *check*
  verb after the agent's write — gates always run in check mode.
- I5: payload decoding failures and missing-input asks happen before any
  session tokens are spent.

Tests: scripted fake-agent harness (deterministic tool-call scripts) driving:
empty-diff vacuous green; three-round converge; exhaust; out-of-set write
(R3); gate flake (gate red→green across rounds); headless missing-payload.

### R7. Outward actions: gates-then-act atomicity and approval

Failure mode: publishing with red or stale gates; acting twice on retry;
acting without consent.

Invariants:
- I1: gates re-expand inputs immediately before the outward step; any drift
  between gate evaluation and act aborts (re-run gates, do not act).
- I2: outward steps are idempotency-guarded where the provider allows
  (publish checks version existence first; PR-open checks for an existing
  branch/PR and updates rather than duplicates) and classified by
  side-effect tier for undo semantics.
- I3: `approval: "required"` blocks in a durable, resumable way (the human
  request outlives the process; a crashed CLI does not lose the approval or
  double-act on resume).
- I4: secrets reach only the outward child process, as placeholders
  substituted at the edge (existing SecretProxy law).

Tests: registry-fake publish double-invoke; kill between gates-green and act
(resume must re-gate); approval denial path; secrets absent from every log
and every cache entry (scan-based test).

### R8. Services lifecycle

Failure mode: leaked servers after failed tests; readiness deadlock; port
collision between concurrent targets flaking CI.

Invariants: acquire/release in a scope that survives keep-going failure
collection; readiness has a timeout with the serve target's captured output
attached to the failure; refcounted sharing within a command; hard teardown
(process-group kill) on interrupt.

Tests: failing consumer still tears down; two consumers one service (single
spawn); readiness-timeout path; SIGINT during test with service up.

### R9. Resolver correctness and incrementality

Failure mode: a missed import edge marks live code dead (deadCode deletes it)
or misses invalidation (stale test skipped); an over-broad closure destroys
the incrementality the feature exists for.

Invariants:
- I1: unresolved specifiers are explicit rows; set-algebra assertions fail on
  unresolved-by-default.
- I2: row cache invalidates on file digest, resolver config digest, and
  resolver implementation fingerprint — nothing else; touching one file
  re-resolves one row.
- I3: closure results are stable across hosts (sorted, path-relative).
- I4: dynamic import expressions and non-literal requires degrade loudly
  (row marked dynamic → closure marked over-approximate → deadCode-style
  consumers refuse unless configured).

Tests: golden closures over fixture trees (cjs/esm/tsconfig-paths/exports
maps); mutation tests (edit one file, count re-resolved rows); the whatsabi
`reachable`/`deadCode` pair as an end-to-end conformance case; adversarial
`import("./" + x)`.

### R10. CI generation drift and affected-mode fidelity

Failure mode: generated workflows drift silently, or affected-mode skips a
target whose inputs actually intersected the change (a wrong green).

Invariants: byte-exact check mode (existing `smthrs ci` comparison law);
`preserve` never overwritten; affected-mode decisions derive from the same
expanded-input machinery as cache keys (one implementation, two consumers) so
"affected" can never disagree with "would re-key".

Tests: golden yml fixtures; preserve-list fixture; affected simulation
harness — for a matrix of synthetic diffs, assert
affected(target) ⇔ key(target) changed.

### R11. Typing without lying

Failure mode: the typed surface rejects the design-partner files (the spec) or
accepts nonsense that explodes at graph load.

Invariant: the vendored artsy PACKAGE.ts/WORKSPACE.ts files type-check
verbatim (minus the reference directive) against the shipped types, in CI
(conformance fixtures, §7). Where the examples are looser than we want (e.g.
`S.Test({toBe: "empty"})` string), the type narrows to the observed literals,
never wider.

## 7. Conformance fixtures: the spec as a test suite

Vendor snapshots of the two design-partner trees' declaration files (only the
S-API files + minimal tree stubs, not the whole repos) into
`packages/targets/test/conformance/{whatsabi,force}/`:

- **Level 0 — types**: files type-check against shipped types.

  and the public target inventory match a golden manifest.
- **Level 2 — plan**: `graph`/`query` over `//...` yields golden plans (edges,

- **Level 3 — dry execution**: with a stub tool runner and fake agent layer,
  `ci`-equivalent plans execute with correct ordering, gating, vacuous-green,

- **Level 4 — live smoke** (this repo only): the flows repo's own ported
  PACKAGE.ts tree runs real builds/tests through the new engine.

Levels 0-3 are CI gates from the first phase they apply to. Any intentional
API change edits the fixture and the golden in the same commit — the fixtures
are the spec's regression lock, which matters because the spec is code that
nobody executes otherwise.

## 8. Phasing

Each phase ends green on its conformance level, with the riskiest invariants
from §5 landed as tests in the same phase as their subsystem — never later.

**Phase 0 — decisions + skeleton.**
Write the decision records (§4) into `docs/specs/Concepts/` (new: `Package
Files.md`, `Target Flavors.md`, `Edge Types.md`, `Artifact Store.md`,
`Resolver.md`, `Agent Targets.md`), resolving the §9 questions with will where
marked. Type skeleton for the S namespace. Vendored conformance fixtures.
Exit: Level 0 passes.

**Phase 1 — the file model.**
PACKAGE.ts/WORKSPACE.ts discovery + loader identity (D1, D2), `S.Package`
public map + labels, `S.Workspace` layers with `Runtime`/`PackageManager`/

`Filegroup`/`Suite`/`Alias`, flavor metadata (D3), edge typing (D4/R5).
Planner + `graph`/`query` work over the new tree. R1 and R5 tests.
Exit: Levels 1-2 pass.

**Phase 2 — execution core.**
`Shell.{Build,Test,Run,Diff}`, `Generate` (3 forms), `Copy`, modes
(check/write/fix), artifact capture + CAS + materialization + `Materialize`
(D5/R4), toolchain-in-keys (R2-I5) — the "turn the cache on" milestone.
`S.Test`/`S.Files.difference` over filegroup-shaped sets. R2, R3, R4 tests.
Exit: Level 3 for shell/generate targets; this repo's first ported packages
build through it.

**Phase 3 — services, gates, git, outward.**
`Shell.Serve` + `readiness` + `services` (D8/R8), `gates` edges,
`Git.Commit`/`Git.Pr`, `Npm.Pack/Publish/Published`, `Api.Compat`,
`Github.Pages/Release`, approval plumbing + side-effect tiers (D9/R7),
`gitDiff` enrichment (D11).
Exit: Level 3 full for non-agent targets.

**Phase 4 — agent targets.**
`S.Agent.{Codex,Lint,Diff,Pr}`, `S.Input.*`, `S.Mcp.Http`, scratch-overlay
write-set enforcement, gates feedback loop, vacuous green, `onSuccess`
(D7/R6, R3 for agents). Fake-agent conformance harness.
Exit: Level 3 full; whatsabi triage-address and force fix-sentry-issue dry-run
green against the fake agent.

**Phase 5 — resolver.**
Row engine, `ImportClosure`, `Files` algebra with unresolved discipline,
`Markdown.CodeBlocks`, then `Bundler.make` + `Bundler.Rspack`
resolve/build (D10/R9).
Exit: whatsabi `reachable`/`deadCode`/`checkReadme` and force
`importGraph`/`unreachableCode`/storybook closure conformance cases pass.

**Phase 6 — CI gen + triggers.**
`Github.Setup/Workflow/CiGen` (+ `Ci` sugar decision), affected mode wired to
input expansion, `Cron` (D12, D13, R10).
Exit: force `.github/PACKAGE.ts` and whatsabi `githubCi` render golden ymls;
affected-equivalence harness green.

**Phase 7 — the port and the deletion.**
Port this repo's BUILD.ts tree to PACKAGE.ts/WORKSPACE.ts; move repo-specific
tool targets (TsBuild, Vitest, DocsParity, ...) into local plain-function
macros or delete in favor of `Shell.*`; regenerate CI; delete the BUILD.ts
loader path, the tool-named catalog, `smthrs`-era docs; update
`packages/build/docs/` wholesale.
Exit: Level 4; repo CI runs on the new engine only.

Phases 2-6 after Phase 1 are largely independent at the interface level;
parallel lanes work if R-tests land with their phase. The fs-package
convergence (shared discovery substrate, §1) is deliberately *after* this
plan's scope: nothing here may make it harder (D1's loader-owned identity and
the shared doctrine keep the door open).
